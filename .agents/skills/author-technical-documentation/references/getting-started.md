# Getting-started pages

## Rules

- This reference **MUST** be applied only when the page is classified as `getting-started`. Why: Getting-started content has unique safety and scope constraints.
- Getting-started pages **MUST** optimize for the shortest verified path to a successful result. Why: New users need momentum first.
- Getting-started pages **MUST** use one happy path and **MUST NOT** branch into optional variants unless the variation is unavoidable. Why: Decision overhead slows onboarding.
- Getting-started pages **MUST** use the default structure below, including prerequisites, a verified path, a verification step, and next steps. Why: The reader needs predictable progression.
- Commands and expected results **MUST** be executable and verified as written. Why: First-run failures destroy trust.
- Getting-started pages **MUST NOT** turn into long tutorials, concept essays, reference pages, or production deployment guides. Why: Their job is first success.

## Default structure

1. one-sentence outcome statement
2. `## What you will build` or `## What you will achieve`
3. `## Prerequisites`
4. `## Install`
5. `## Create the project` or `## Run the sample`
6. `## Verify it works`
7. `## What happened`
8. `## Summary`
9. `## Next Steps`
